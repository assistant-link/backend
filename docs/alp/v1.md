# Assistant Link Protocol (ALP), version 1

ALP is the public API an agent uses to connect to an Assistant Link service: it pairs once with a short code the user
gives it, then holds a WebSocket open so the user's Assistant shows as online and the service can deliver the user's
messages to the agent. The agent sends its own messages to the user over HTTP.
It is built only on established standards (HTTP, JSON, WebSocket, and JSON-RPC 2.0), so any agent runtime can
implement it directly. [`al`](https://github.com/assistant-link/cli) is a reference client; agents do not need it.

The key words MUST, MUST NOT, SHOULD, and MAY are to be read as described in
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

## Terms

- **Assistant**: the user-facing identity of an AI assistant in the app (a name, an avatar, and history).
- **Assistant Link** (Link): a connection between an Assistant and one agent installation. An Assistant may have
  several Links, for example one on a laptop and one in the cloud.
- **Service URL**: the base URL of an Assistant Link service, for example `https://assistant-link.fly.dev` or a
  self-hosted one. Every path below is relative to it.
- **Event**: one item of an Assistant's conversation. v1 delivers one kind, `text_message`: a message the user typed.
- **Position**: the last event a Link acknowledged. The service keeps one per Link, and delivers the events after it.
- **Pairing code**: a short-lived, single-use code the user creates in the app for one Link that is not paired yet.
- **Link token**: the long-lived secret an agent receives in exchange for a pairing code. It authenticates that one
  Link.

## Overview

```
agent                                  service                                app
  |                                       |  <-- user creates a Link and ----  |
  |                                       |      a pairing code                |
  |  <---------- pairing text (pasted by the user) -------------------------  |
  |  POST /alp/v1/pair {"code"}  ------>  |                                    |
  |  <------ 200 {"link_id", "assistant_name", "token"}                        |
  |  GET /alp/v1/connect (WebSocket, Bearer token)  -->                        |
  |  <------ connection.ready             |  ---- Link is online ----------->  |
  |  <------ ping / pong ------------->   |                                    |
  |                                       |  <-- user sends a message -------  |
  |  <------ event.deliver (request)      |                                    |
  |  result {"event_id"} ------------->   |  ---- message is delivered ---->   |
  |  POST /alp/v1/messages {"text"} --->  |  ---- message from the agent -->   |
```

### Pairing text

The app shows the user text to paste to the agent, generated by the service. It names the Assistant and carries the
service URL and the pairing code:

```
Connect to my assistant "Hermes" on Assistant Link.
Follow the instructions at https://assistant-link.fly.dev/install.md
Service: https://assistant-link.fly.dev
Pairing code: K7QM-2XPA (expires 14:32 UTC)
```

`/install.md` on every service gives an agent step-by-step instructions for doing this with `al`. Agents MUST use the
service URL from the `Service:` line for both pairing and connecting.

## Versioning

All ALP endpoints live under the base path `/alp/v1`.

Changes within v1 are additive only: new endpoints, new JSON-RPC methods and notifications, new optional fields, and
new error codes and reasons. Anything that would break an existing v1 agent goes under a new version path.

For this to work, agents MUST:

- ignore JSON fields they do not recognize, in HTTP bodies and in JSON-RPC messages;
- ignore JSON-RPC notifications whose method they do not recognize;
- answer a JSON-RPC request from the service for a method they do not implement with error `-32601` (Method not
  found);
- treat an unrecognized error `code` or `reason` like a generic failure of that kind (HTTP status class, or JSON-RPC
  error).

## Authentication

Every ALP request except pairing MUST carry the Link token:

```
Authorization: Bearer <Link token>
```

Link tokens start with `alt_`, followed by URL-safe base64. Treat the rest as opaque. A request with a missing or
unknown token, or with the token of a Link whose account was deleted, is rejected with `401` and error code
`unauthorized`.

A Link token stays valid until the user deletes their account.

## HTTP errors

Every ALP HTTP error, including a rejected WebSocket upgrade, has a 4xx or 5xx status and this JSON body:

```json
{"error": {"code": "invalid_code", "message": "The pairing code is not valid."}}
```

`code` is a stable snake_case identifier for agents to match on. `message` is for people and may change.

| Status | `code`             | Meaning                                                         |
| ------ | ------------------ | --------------------------------------------------------------- |
| 401    | `unauthorized`     | Missing, unknown, or no longer valid Link token.                |
| 404    | `not_found`        | No such endpoint.                                               |
| 409    | `idempotency_key_conflict` | The `idempotency_key` was used for another message.     |
| 422    | `invalid_params`   | The request body is missing a field or has the wrong type.      |
| 422    | `invalid_code`     | The pairing code is unknown, already used, or was replaced.     |
| 422    | `expired_code`     | The pairing code was valid but has expired.                     |
| 422    | `text_empty`       | The message text is empty or only whitespace.                   |
| 422    | `text_too_long`    | The message text has more than 4,000 Unicode code points.       |
| 500    | `internal_server_error` | The service failed. Retrying later may succeed.            |

## Pairing

```
POST /alp/v1/pair
Content-Type: application/json

{"code": "K7QM-2XPA"}
```

On success the service marks the code used, pairs the Link, and responds:

```
200 OK
Content-Type: application/json

{"link_id": "0199b5c4-...", "assistant_name": "Hermes", "token": "alt_..."}
```

The token is returned only once. The agent MUST store it, together with the service URL it paired with (see
[Security considerations](#security-considerations)).

Pairing codes are 8 characters of [Crockford base32](https://www.crockford.com/base32.html), shown as `XXXX-XXXX`,
and expire after 15 minutes. The service matches a submitted code ignoring case, hyphens, and whitespace, and reads the
letters Crockford base32 leaves out as their look-alikes (`O` as `0`, `I` and `L` as `1`). So `k7qm-2xpa`,
`K7QM 2XPA`, and `K7QM2XPA` are the same code.

Errors: `422 invalid_params` when `code` is missing or not a string; `422 invalid_code` for an unknown, used, or
replaced code; `422 expired_code` for an unused code past its expiry. In every case the user creates a new code in the
app; retrying the same code cannot succeed.

## Agent connection

```
GET /alp/v1/connect
Upgrade: websocket
Authorization: Bearer <Link token>
```

A standard WebSocket ([RFC 6455](https://www.rfc-editor.org/rfc/rfc6455)) upgrade. Over HTTPS, use `wss://`. If the
token is not accepted, the upgrade is rejected with `401 unauthorized` and an [HTTP error](#http-errors) body.

While at least one connection for a Link is open, the app shows that Link, and its Assistant, as online. The service
records when each connection opens and closes and shows the Link's last active time when it is offline. A Link may hold
several connections at once; it goes offline when the last one closes.

### Messages

Every text frame, in either direction, holds exactly one [JSON-RPC 2.0](https://www.jsonrpc.org/specification)
message: a request, a response, or a notification. Batches (JSON arrays) and binary frames are not used: the service
answers one with `-32600`.

Events from the service are JSON-RPC notifications, except `event.deliver`, a request the agent answers. Requests
either side sends get exactly one response with the same `id`.

#### Request ids

Each side numbers its own requests with a counter per connection: the service's `event.deliver` requests are 1, 2, 3, ...
and the agent numbers any request it sends from its own counter. An `id` only pairs a response with its request,
never an event id. A response whose `id` matches no pending request completes nothing and the connection stays open,
except a `result` carrying an `event_id`, which is always [acknowledged](#acknowledging-an-event).

### `connection.ready`

The first message on every accepted connection, sent by the service:

```json
{"jsonrpc": "2.0", "method": "connection.ready",
 "params": {"link_id": "0199b5c4-...", "assistant_name": "Hermes", "protocol_version": "1"}}
```

| Param              | Type   | Meaning                                    |
| ------------------ | ------ | ------------------------------------------ |
| `link_id`          | string | The Link this token belongs to.            |
| `assistant_name`   | string | The Assistant's current name.              |
| `protocol_version` | string | The ALP version of this connection: `"1"`. |

The Link is online from this point on.

### `connection.closing`

When the service closes a connection on purpose, it first sends:

```json
{"jsonrpc": "2.0", "method": "connection.closing", "params": {"reason": "account_deleted"}}
```

then closes the WebSocket. `reason` is a stable snake_case identifier:

| `reason`          | Meaning                                                                          | What the agent does                                           |
| ----------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| `account_deleted` | The user deleted their account. The Link and its token no longer exist.          | Stop. Reconnecting gets `401`; the user must pair again.      |

Agents SHOULD treat an unrecognized `reason` as a dropped connection and reconnect with backoff.

### `event.deliver`

The service delivers an event as a request to the agent. The params are the event:

```json
{"jsonrpc": "2.0", "id": 1, "method": "event.deliver",
 "params": {"id": "01a1735a-38b8-7c7b-a2cb-22dcbdc09310", "type": "text_message",
            "created_at": "2026-10-25T13:57:35.032829Z", "deleted": false, "text_message": {"text": "Hi"}}}
```

| Param          | Type    | Meaning                                                                               |
| -------------- | ------- | ------------------------------------------------------------------------------------- |
| `id`           | string  | The event's id. It stays the same every time the event is delivered.                  |
| `type`         | string  | `text_message`. Agents MUST ignore types they do not know.                            |
| `created_at`   | string  | When the service stored the event, RFC 3339 in UTC.                                   |
| `deleted`      | boolean | `true` when the content was deleted.                                                  |
| `<type>`       | object  | The content, under a key named after `type`. A deleted event has no such key.         |

A `text_message` has `{"text": "..."}`, 1 to 4,000 Unicode code points.

What the service delivers:

- Only messages the user sent, deleted ones included. A message the agent posted itself is never delivered.
- Every Link of an Assistant receives every message, each at its own [position](#terms). A Link receives only messages
  stored after it was paired. A message stored at the moment of pairing may arrive or not.
- One event at a time per Link, in the order the user sent them; the next follows the acknowledgement. A message stays
  deliverable until a Link acknowledges it, so after `connection.ready` an agent that was offline catches up.

#### Acknowledging an event

The agent acknowledges an event by answering the request with a `result`:

```json
{"jsonrpc": "2.0", "id": 1, "result": {"event_id": "01a1735a-38b8-7c7b-a2cb-22dcbdc09310"}}
```

Answer only after the agent has taken the event, for example after it wrote it to where it will be read: the service
does not send it again. The position of the Link then moves to that event, and the user's app shows the message as
delivered once any Link of the Assistant acknowledged it.

The service honors a `result` with an `event_id` from any request or connection, however late: after the 30 seconds
below, on another connection of the Link, or for an `id` it no longer waits for. An `event_id` it cannot use is
ignored, without an error, and the connection stays open: an unknown id, an event of another Assistant, one that is
not a message of the user, and an event at or below the position of the Link. The last one is expected: the service
may send an event twice, and the second acknowledgement changes nothing.

#### Failed deliveries

An agent that does not implement `event.deliver` answers error `-32601`. An agent that cannot take the event now
answers error `-32001` with `data.reason` `not_received`:

```json
{"jsonrpc": "2.0", "id": 1,
 "error": {"code": -32001, "message": "Not received.", "data": {"reason": "not_received"}}}
```

An error response, a closed connection, and no response within 30 seconds only fail that attempt. The position does
not move, the connection stays open, and the service sends the same event again with the same `id`. It sends it to
the Link's next-newest connection that has not failed it. When every open connection failed it, it tries again after
30 seconds, then after 60, doubling per failed round up to 5 minutes. A new connection resets the wait and starts a
round at once.

Delivery is at least once. A lost or late acknowledgement delivers the event again. The agent is responsible for
de-duplicating: it remembers the `id`s it handled. The service does not de-duplicate for it.

### Methods

The service defines no methods an agent can call: a request for any method gets error `-32601`. Methods and
notifications added later in v1 follow the rules in [Versioning](#versioning).

### JSON-RPC errors

The service answers malformed or unsupported messages with a standard JSON-RPC error response and keeps the
connection open:

| Code               | Meaning                                                                                   |
| ------------------ | ----------------------------------------------------------------------------------------- |
| `-32700`           | Parse error: the frame is not valid JSON. `id` is `null`.                                  |
| `-32600`           | Invalid request, including a batch or a binary frame. `id` is echoed when it is valid.   |
| `-32601`           | Method not found.                                                                         |
| `-32602`           | Invalid params.                                                                           |
| `-32000`..`-32099` | ALP errors. `error.data.reason` holds a stable snake_case reason to match on.            |

```json
{"jsonrpc": "2.0", "id": 1, "error": {"code": -32601, "message": "Method not found: something.new"}}
```

### Liveness

The service sends a WebSocket ping at least every 25 seconds. Agents MUST answer pings with pongs, as RFC 6455
requires; most WebSocket libraries do this on their own. The service closes a connection from which it has received
no frame, pongs included, for 60 seconds, and the Link goes offline.

Agents SHOULD treat a connection on which nothing has arrived for 60 seconds as lost, since the service pings well
within that time and a half-open TCP connection may otherwise never report an error.

### Reconnecting

An agent that wants to stay online SHOULD reconnect whenever the connection drops, with exponential backoff and
jitter (for example from 1 second up to a 30 second cap, reset once a connection has stayed up for a minute). It
SHOULD retry network errors, `5xx` responses, and dropped connections indefinitely, and SHOULD stop on `401` and on
`connection.closing` with `account_deleted`. Other `4xx` responses to the upgrade usually mean a wrong service URL,
which retrying cannot fix.

## Send a message to the user

```
POST /alp/v1/messages
Authorization: Bearer <Link token>
Content-Type: application/json

{"text": "Your reminder is set.", "idempotency_key": "01a17359-a083-7537-9aab-4a1a9cddc7d3"}
```

On success the service stores the message as the Assistant's, shows it to the user, and responds:

```
201 Created
Content-Type: application/json

{"message_id": "01a17359-bdb4-7d6a-9de3-af603ed38a1b", "created_at": "2026-10-25T13:57:03.540992Z"}
```

- `text` is 1 to 4,000 Unicode code points, not only whitespace, and without U+0000. Otherwise the service responds
  `422` with `text_empty`, `text_too_long`, or `invalid_params` (also for a missing or non-string `text`) and stores
  nothing.
- It works whether or not the Link is online, and does not change the Link's presence or last active time.
- The message is not delivered to any Link of the Assistant, this one included.
- `idempotency_key` is optional: a UUIDv7, unique per account: a key already used by another Link of the account or sent by the app responds `409` `idempotency_key_conflict`. A request repeated with the same key and text responds
  `200` with the `message_id` and `created_at` of the stored message, even if its text was deleted since, and stores
  nothing new. The same key with another text responds `409` `idempotency_key_conflict`. A key that is not a UUIDv7
  responds `422` `invalid_params`. Without a key, a request repeated after a lost response stores the message twice.

## Link status

```
GET /alp/v1/link
Authorization: Bearer <Link token>
```

```
200 OK
Content-Type: application/json

{"link_id": "01a17359-7ec0-7712-be6b-4024e7ed246e", "assistant_name": "Hermes", "unread_count": 1}
```

`unread_count` is the number of the user's messages after the Link's position, the ones `event.deliver` would still
deliver. The request only counts: it does not open a connection, and changes neither the position, the Link's
presence, nor its last active time.

## Security considerations

- **The Link token is a bearer credential.** Anyone holding it can connect as that Link. Store it readable only by the
  agent's OS user (for example a file with mode `0600`), never log it, and never pass it on a command line.
- **Bind the token to its service.** Store the service URL the token was issued by, and send the token only to that
  service. If the agent is later pointed at a different service URL, it MUST NOT send the stored token there. `al`
  compares the two URLs after dropping trailing slashes and lowercasing the scheme and host.
- **Use TLS.** Over the internet, use `https://` and `wss://` and verify the service's certificate. Plain `http://` is
  for a service on `localhost` or a private network.
- **Trust boundaries.** The agent connects outbound only, so its host needs no open port. The service trusts whoever
  holds a valid Link token for that Link; the agent trusts the service URL it was given in the pairing text.
- **Messages are input for your model.** Every Link of an Assistant receives every message the user sends it, so pair
  a Link only for an agent the user trusts. What the agent does with the text is its own trust boundary.
- **A leaked Link token can act as the Assistant.** Its holder can post messages as the Assistant, read the messages
  after the Link's position, and mark messages delivered.

## Example session

```sh
SERVICE=https://assistant-link.fly.dev

curl -s -X POST "$SERVICE/alp/v1/pair" -H 'content-type: application/json' -d '{"code": "K7QM-2XPA"}'
# {"link_id":"0199b5c4-...","assistant_name":"Hermes","token":"alt_..."}

curl -s "$SERVICE/alp/v1/link" -H "Authorization: Bearer alt_..."
# {"link_id":"0199b5c4-...","assistant_name":"Hermes","unread_count":0}

curl -s -X POST "$SERVICE/alp/v1/messages" -H "Authorization: Bearer alt_..." -H 'content-type: application/json' \
  -d '{"text": "Your reminder is set."}'
# {"created_at":"2026-10-25T13:57:20.386135Z","message_id":"01a17359-ff82-7160-a51e-fddb0b093dbf"}
```

Holding the connection and acknowledging each event, in Node.js 22 or later (no packages):

```js
const service = "wss://assistant-link.fly.dev";
const token = "alt_...";

const ws = new WebSocket(`${service}/alp/v1/connect`, { headers: { authorization: `Bearer ${token}` } });
ws.onmessage = ({ data }) => {
  const message = JSON.parse(data);
  if (message.method !== "event.deliver") return console.log(message);
  console.log(message.params.text_message?.text); // take the event first, then acknowledge it
  ws.send(JSON.stringify({ jsonrpc: "2.0", id: message.id, result: { event_id: message.params.id } }));
};
// { params: { protocol_version: '1', link_id: '0199b5c4-...', assistant_name: 'Hermes' }, method: 'connection.ready', jsonrpc: '2.0' }
// Remind me to call David
```
